## Additional defects found during the independent re-audit

Running Forge against its own source (`forge all audit`) surfaced a defect not named in the audit
report: `isNoSqlSink` matched a bare `.find` on any receiver, and `isModelWriteSink` matched bare
`create`, `update`, `insert`, `save`, and `assign`. Every `Array.prototype.find` and every
`Object.assign` in ordinary code was therefore reported as a database query or a persistence
boundary.

Measured effect on Forge's own source:

|                 | Before | After |
| --------------- | ------ | ----- |
| Total findings  | 63     | 42    |
| `FAIL` findings | 28     | 5     |

The five remaining `FAIL` findings are vulnerable code deliberately embedded in
`cli/tests/*.test.ts` as analyzer fixtures, which is expected. Ambiguous method names now require a
data-access receiver; unambiguous ORM methods (`findMany`, `aggregate`, `updateMany`, `deleteMany`,
`updateOne`, `insertOne`) are unchanged. Regression tests cover both the suppressed false positives
and a genuine ORM call that must still be detected.

## Remaining NOT_VERIFIED limitations

- Coverage measurement was not run in this pass.
- Analyzers still inspect test files, so vulnerable fixture code inside a test is reported as a real
  finding. Excluding tests wholesale was rejected because it would also hide genuine defects in test
  utilities; this is recorded as a known limitation rather than silently filtered.
- The taint engine is intra-file only. Cross-file propagation, dynamic property access, and
  reflective call targets are unresolved and are reported as such, never inferred as safe.
- Route adapters do not resolve middleware-inherited visibility; those routes report `unknown`.
- Analyzer coverage for Python, Go, Rust, and JVM sources is `none`; the support registry names the
  adapter each would require.
- Runtime, operational, and provider-side verification (real query plans, backup restoration,
  scanner state, keyboard-only workflows, focus management) remains manual by design.
